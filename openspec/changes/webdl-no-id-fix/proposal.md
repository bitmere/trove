# Web download add fails with "TorBox returned no web download id"

## What the user asked for

On 0.1.31, adding a web link in the Add sheet fails with
"TorBox returned no web download id". The user asked to fix all six
items of the plan: switch webdl and usenet adds to the sync create
endpoints, recover from mylist when a create returns no id, surface
TorBox's detail on the success-without-id path, add redacted
diagnostic logging of the create response, handle 422
detail-as-array in `safeDetail`, and add tests for the webdl +
usenet add paths.

## Verified current state

- The string is generated by the app, not by TorBox. It is the
  `detail` of a `DebridError.Provider("create", …)` thrown at
  `TorBoxProvider.kt:243`, and the Add sheet shows that detail
  verbatim (`AddViewModel.kt:169-171`). TorBox's own message, if
  any, is never in it.
- To reach line 243, `parseEnvelope()` (`TorBoxProvider.kt:99-118`)
  must have returned normally, which requires HTTP 2xx AND
  (`success` absent OR `success == true`). Every documented TorBox
  failure mode — `success:false`, non-2xx, 401, 429, unreadable body
  — throws a different error before line 243. The response TorBox
  sent was, by the app's own reading, a success with no usable id:
  `data` was `null`, not an object, or an object containing neither
  `webdownload_id` nor `queued_id`.
- The webdl branch calls the async endpoint
  `POST /webdl/asynccreatewebdownload` (`:234-245`) and the usenet
  branch calls `POST /usenet/asynccreateusenetdownload` (`:246-256`),
  then both demand an id. The magnet branch's own comment (`:208`)
  says "Synchronous creation returns the ID and refusal detail;
  async returns data=null" — yet the webdl and usenet branches use
  async and throw if there is no id.
- The spec (`~/workspace/torbox-app/torbox-openapi.json`) documents
  both sync endpoints: `POST /v1/api/webdl/createwebdownload`
  (form-urlencoded `link`) and
  `POST /v1/api/usenet/createusenetdownload` (multipart file). The
  sync webdl response is the one with a documented-by-example id:
  the Postman example returns
  `{"hash", "webdownload_id": "0", "auth_id"}` and the official Go
  SDK types `WebdownloadId` as a string. No async response example
  or SDK method exists anywhere checked.
- The id read already tolerates numeric and numeric-string ids
  (`optLong`, `ProviderHelpers.kt:56-60`), so a string id is not the
  cause.
- `safeDetail` (`TorBoxProvider.kt:124-137`) reads `detail` only as
  a string (`optString`). A 422 validation error carries `detail`
  as an array of `{loc, msg, type}`, so the real field-level message
  is dropped and the user gets the generic fallback.
- There is no logging anywhere in `TorBoxProvider.kt`, so the actual
  response that produced the error cannot be reconstructed after the
  fact. `core` is Android-free and has no logging facility today.
- No test covers the webdl or usenet add path at all:
  `TorBoxProviderTest.kt` tests only the magnet create (`:332-356`)
  and the error-envelope preservation (`:497-499`).

## Proposed change

- Switch the webdl add to the sync endpoint
  `POST /webdl/createwebdownload` (same form field `link`) and the
  usenet add to `POST /usenet/createusenetdownload` (same multipart
  file upload), matching the torrent branches. Keep the same id
  reads (`webdownload_id ?: queued_id`,
  `usenetdownload_id ?: queued_id`) and the same app-side hourly
  budget guard on webdl.
- When a create still returns no id, recover from mylist instead of
  throwing: look the item up by hash via `GET /webdl/mylist` with
  `bypass_cache=true` (webdl `hash` is the MD5 of the link) or, for
  usenet, by the `hash` the create response itself carried via
  `GET /usenet/mylist` with `bypass_cache=true`. Return the matched
  row; only throw if it is absent. Never retry the create
  (double-add risk).
- When the no-id path does throw, include TorBox's `detail` string
  in the thrown error (through the existing `safeDetail` redaction)
  instead of always replacing it with the generic line, so a
  server-side refusal carried in `detail` is visible.
- Log a redacted diagnostic line when a create returns no id:
  endpoint, HTTP status, `success`, the (redacted) `detail`, and
  which id fields were present — never the link, the key, or the
  full body. `core` stays Android-free: a minimal injectable
  diagnostic sink (no-op by default) wired to platform logging at
  the app's `TorBoxProvider` construction sites.
- Handle 422 `detail`-as-array in `safeDetail`: render the first
  `ValidationError.msg` with its `loc`, under the same redaction
  (key / `requestdl` / `http` filter) and length cap.
- Add tests for the webdl + usenet add paths: numeric and string
  ids, `queued_id`, `data` null / empty, hash-only data (recovered
  from mylist), and a `success:false` `DUPLICATE_ITEM` case
  asserting the real detail surfaces; plus a 422 detail-as-array
  case and a diagnostic-sink capture case.

## Non-goals

- No live-API confirmation against TorBox (needs the user's
  account/key and go-ahead — skipped).
- No retry of the create call on a missing id; no treating a
  missing id as success unconditionally (a refused/offline link
  must not show a phantom queued row).
- No new request fields (`name`, `password`, `as_queued`,
  `add_only_if_cached`); no change to the torrent branches, the
  rate budgets, or the Add sheet UI.
- No version bump, changelog entry, PR, merge, tag, or release.
